# Hybrid knowledge base retrieval and the operations view

This change makes knowledge base retrieval smarter and gives the team a view of what AI triage costs and how well it runs. It has five parts.

1. Hybrid retrieval. Postgres full text search plus the existing pgvector similarity, merged with reciprocal rank fusion (RRF).
2. Eighteen new UK MSP runbook articles, taking the knowledge base from 12 to 30.
3. A retrieval quality test with 20 queries, comparing hit rate at 3 for vector only and hybrid search.
4. An `/ops` page backed by `GET /api/ops/metrics`.
5. Structured JSON logs with a request id on every API request, returned as `X-Request-ID`.

## Owner actions

| Step | Why |
|---|---|
| Apply `supabase/migrations/004_hybrid_kb_search.sql` in the Supabase SQL editor | Adds the `search_tsv` column, its GIN index and `match_kb_hybrid`. It has **not** been applied. Until it is, retrieval stays vector only and nothing breaks. |
| Open `/api/health` once after deploying | The health check now tops up a knowledge base with fewer than 30 articles, so the 18 new articles are embedded and inserted. It works in batches of two and stops after about 25 seconds, so it can take two or three calls. |
| Optional. Run `python scripts/eval_retrieval.py` with the production environment loaded | Repeats the 20 query comparison with real gte-small embeddings against the real database. Read only. |

The migration is safe to apply on a live database. The column is generated by Postgres, so no backfill is needed, and the grant matches `match_kb` (only `triage_api` can execute it).

## 1. Hybrid retrieval

**Why.** Dense embeddings are good at paraphrase but weak on exact identifiers such as `0x80070643`, `DMARC` or a product name. Full text search is the opposite. RRF combines the two by rank only, so there is no need to calibrate cosine distances against `ts_rank` values.

**How it works.** `match_kb_hybrid(query_embedding, query_text, match_count, rrf_k, candidate_count)`

1. Ranks up to 20 articles by cosine distance.
2. Ranks up to 20 articles by `ts_rank_cd` over `search_tsv`, where the title has weight A, the category B and the body C.
3. Scores every article `1 / (60 + rank)` for each list it appears in, sums the scores, and returns the top three (at most five).

Ticket text is long and conversational, so the keyword query ORs every term. `plainto_tsquery` would AND them and almost never match a whole ticket. A query made only of stop words simply returns the vector ranking.

**Fallback.** `rag.search` calls `match_kb_hybrid` first, inside its own savepoint. If the function, column or grant is missing it falls back to `match_kb`, logs one warning and stays vector only for five minutes before trying again, so a warm serverless instance notices soon after the migration lands. Any other database error falls back for that one call only. This was checked against a real Postgres 16 with pgvector, including inside an outer transaction.

**Audit trail.** The `kb_matched` event now records `"method": "hybrid"` or `"vector"`, and the copilot `search_knowledge_base` tool reports `hybrid` when it was used.

**Code.** `triageops/hybrid.py` (fusion and the retry switch), `triageops/rag.py` (search and fallback), `store.match_kb_hybrid`, migration 004.

**Seeding.** Still idempotent: an advisory lock lets one instance seed at a time, and `ON CONFLICT (slug) DO NOTHING` makes a repeat harmless. Every embedding call still carries at most two texts because of the edge function CPU limit. Three things are new.

1. The health check seeds whenever there are fewer articles than `KB_ARTICLES`, not only when the table is empty. Without this, an existing database would never receive the new articles.
2. A run stops starting new batches after 25 seconds and inserts what it has. The next call carries on. This keeps the health check well inside the 60 second function limit.
3. If a batch fails, earlier batches are still inserted, and the health check waits ten minutes before trying again, so a failing article does not slow down every poll.

## 3. Retrieval quality test

`tests/test_retrieval_quality.py` runs 20 realistic ticket texts (in `tests/retrieval_cases.py`), each with the article that should answer it. The cases cover all 18 new articles and two of the originals.

No real model runs in CI, so `tests/retrieval_fakes.py` provides deterministic stand-ins. The fake embedder hashes text features into 384 dimensions. No hashing trick behaves like gte-small, so rather than pick one that flatters hybrid search, the test runs five feature modes and checks all of them. The keyword ranker mirrors `search_tsv`, with English stop words, rough stemming, the A, B and C weights and no IDF. Fusion uses the same RRF function as production.

Hit rate at 3 over the 20 queries.

| Fake embedder | Vector only | Hybrid (Python mirror) | Hybrid (real Postgres 16) |
|---|---|---|---|
| Whole words | 0.80 | 0.85 | 0.85 |
| Words without stop words | 0.85 | 0.95 | 0.95 |
| Stems | 0.90 | 0.95 | 0.95 |
| Character trigrams | 0.95 | 0.95 | 1.00 |
| Stems and trigrams | 1.00 | 1.00 | 1.00 |

The last column comes from loading the same fake vectors into a local Postgres with pgvector, applying migrations 001 to 004 and calling `match_kb_hybrid`. It was a one off check during development and is not part of the test suite, which never touches a database.

The test asserts that hybrid is never worse than vector only for any mode, that hybrid reaches at least 0.85 for every mode, and that hybrid is better on average. Keyword search alone scores 0.75, so neither retriever is enough by itself. These numbers measure the method, not production quality. The script in the owner actions gives the real figure with gte-small.

## 4. Operations view

**Endpoint.** `GET /api/ops/metrics?days=14` (1 to 90, default 14). No authentication, like `/api/stats`, because it returns only aggregates.

It reads one narrow row per ticket in the window (`created_at`, `ai_model`, `ai_latency_ms`, token counts, `priority`, `sla_due_at`, `sla_breached`) and computes everything in `triageops/ops.py`. No schema change is needed.

| Field | Meaning |
|---|---|
| `totals.cost_usd`, `cost_per_ticket_usd` | Tokens times list price, in US dollars. Haiku 5.5 $0.10 and $0.50, Sonnet 5.5 $2 and $10, Opus 5.5 $4 and $20, Fable 5.1 $10 and $50 per million input and output tokens. Dated model ids match by prefix. Unknown models count as zero and are reported in `unpriced_tickets`. |
| `totals.input_tokens`, `output_tokens` | Summed from the ticket columns. |
| `latency_ms.p50`, `p95` | Over tickets triaged by Claude. Keyword fallback runs in milliseconds and would flatter the figure, so it is excluded, as in `/api/stats`. Linear interpolation, the same as Postgres `percentile_cont`. |
| `model_mix` | Tickets, share, tokens, cost and latency per `ai_model`, including `rules-fallback`. |
| `fallback_rate` | Fallback tickets divided by tickets that reached the AI step. |
| `sla` | Breaches in the window, breach rate over tickets with an SLA, and breaches by priority. |
| `daily` | One row per UK calendar day, with zero rows for quiet days. |
| `truncated` | True if the window held more than 50,000 tickets and only the first 50,000 were read. |

Days are UK calendar days (Europe/London), so a ticket at 23:30 UTC in summer counts towards the next day. Copilot chat tokens are not stored per ticket, so spend covers triage only. The page says so.

**Page.** `/ops`, linked from the header as Operations. Six headline figures, a cost per day column chart with hover and keyboard tooltips and a full table view, the model mix and SLA breaches by priority. It refreshes every 30 seconds while the tab is visible, offers 7, 14 and 30 day ranges and works at phone width. It is lazy loaded with its own stylesheet, so the dashboard bundle is unchanged.

## 5. Structured logs and request ids

`triageops/observability.py` adds a pure ASGI middleware and a JSON log formatter.

* Every response carries `X-Request-ID`. A caller may send its own, such as an n8n run id. It is reused only if it is 8 to 64 characters of letters, digits, dots, dashes or underscores, so log lines cannot be forged through the header. Otherwise a new id is generated.
* Every log line is one JSON object on stderr with `ts`, `level`, `logger`, `message`, the `request_id` when there is one, and any `extra` fields. Lines logged inside sync routes carry the id too, because the context variable is set before the thread pool runs the handler.
* One access line per request records method, path, status and duration. It leaves out the query string, because the ticket search box puts free text there, and the client IP, which the service never stores.
* Under uvicorn (the Docker and systemd kits), uvicorn's own access log is switched off because it records IPs and query strings, and its other messages go through the JSON handler. No deploy file needed to change.
* The frontend keeps the id on `ApiError.requestId`, and the `/ops` error message shows it as a reference to quote.

```json
{"ts": "2026-11-04T15:45:14.346+00:00", "level": "error", "logger": "triageops.access", "message": "GET /api/health 503", "request_id": "b59c05feedd74b31b9e4993187aec1ab", "event": "http_request", "method": "GET", "path": "/api/health", "status": 503, "duration_ms": 14.3}
```
